# FinTrace 企业级硬化评审

## 总评

站在金蝶/用友企业级费控 Agent 团队视角，FinTrace 是一个产品判断很清楚的 MVP：三层决策链、字段溯源、红蓝评测、人机复核和 DeepSeek 门控方向都对。

但它还不是能直接交付企业客户的系统。当前差距不在“业务逻辑有没有想法”，而在企业级硬化：异构解析、异常治理、服务边界、并发控制、存储审计、配置治理和 LLM 数据安全。

## 1. Parser 与异构票据解析

当前能力：已经支持 ERP 结构化行、OCR/聊天文本、字段 alias、金额冲突和来源记录。

企业风险：真实客户现场会有多种票据模板、地区格式、币种格式、OCR 噪声、字段缺失和多来源冲突。单纯依赖行级规则和正则，容易在第一批真实数据里暴露字段抽取不稳定。

硬化要求：

- 按票据类型拆解析器：增值税发票、行程单、酒店水单、餐饮小票、采购附件。
- 建立字段融合策略：ERP、OCR、附件文本、审批聊天多来源冲突时保留候选值、置信度和裁决理由。
- 增加 parser 专用黄金集：覆盖金额格式、日期格式、发票号相似、供应商别名、OCR 误识别。

优先级：最高。Parser 错了，后面的规则、RAG、LLM 都是在错误字段上做推理。

## 2. 异常 taxonomy 与恢复策略

当前能力：case 级失败会回退到 `MANUAL_REVIEW`，批次不会整体回滚；DeepSeek 调用失败会留下 fallback meta。

企业风险：所有异常都只按“失败后回退”处理，会掩盖系统性故障。例如 OCR 通道连续失败、LLM API 限速、文件权限错误、配置损坏，恢复策略完全不同。

硬化要求：

- 定义异常分类：输入数据错误、解析错误、外部服务超时、LLM JSON 错误、限流、权限、配置、存储写入失败。
- 按分类配置 retry、退避、熔断、降级和告警。
- 把 error registry 从“结果文件”升级为可查询的运维事件。

## 3. 服务/API 边界

当前能力：CLI、Streamlit 和 Python import 可以跑完整流程。

企业风险：第三方 ERP/费控/财务共享系统无法稳定集成 Python 内部函数；前端直接触发批处理会阻塞用户体验。

硬化要求：

- 推理引擎拆成 HTTP/gRPC 服务。
- 前端只调用 API，不直接 import 引擎。
- 批量审核走异步 job：提交批次、查询状态、下载结果、失败重试。
- 对外暴露稳定接口：`submit_batch`、`get_batch_status`、`get_case_result`、`record_manual_review`。

## 4. 并发、限流与吞吐

当前能力：`ThreadPoolExecutor` 可以并行处理 case。

企业风险：线程池没有租户级限流、外部 API 速率保护和资源池，容易在大批量报销单或多人同时使用时触发 429、部分失败和结果不一致。

硬化要求：

- 增加租户级、批次级、LLM/OCR 通道级 rate limit。
- 引入任务队列和 worker 池，限制同一客户并发。
- 压测 1 万、10 万 case 的吞吐、失败率、平均延迟和 P95/P99 延迟。

## 5. 存储与审计日志

当前能力：本地 `runtime/batches/<batch_id>/` 保存 manifest、case_result、batch_result 和 traces。

企业风险：本地文件没有事务、版本、权限、审计留痕和跨机器一致性。财务单据的状态变化需要长期留存和不可抵赖。

硬化要求：

- 用 PostgreSQL 或企业数据库保存批次、case、字段候选、决策、人工复核和事件日志。
- 每次状态变更记录操作人、时间、前后值、原因和来源系统。
- 文件产物只作为导出和调试缓存，不作为唯一事实源。

## 6. 配置治理

当前能力：默认规则 JSON 加环境变量/运行时覆盖，已经比写死在代码里好。

企业风险：部署人员需要清楚知道配置优先级、校验规则、生效时机和回滚方式。否则规则改动会变成不可追溯的生产风险。

硬化要求：

- 给规则配置加 schema 校验和启动前检查。
- 输出配置来源和 diff。
- 支持规则版本、灰度、回滚和影响评估。
- 面向企业环境可接 Apollo/Nacos/配置中心。

## 7. LLM 数据安全

当前能力：DeepSeek 是增强层，不允许覆盖阻断控制；API Key 来自环境变量，错误信息有最小脱敏。

企业风险：报销单包含员工、供应商、客户、金额、审批聊天等敏感信息。直接发送给外部模型会触发数据合规、客户隔离和信披风险。

硬化要求：

- LLM 前增加 PII/敏感字段扫描与脱敏。
- 明确哪些字段允许出域，哪些只能本地推理。
- 对模型输入输出做租户隔离、日志脱敏和最小化存储。
- 给 DeepSeek/其他模型供应商建立数据处理协议和开关策略。

## 企业交付路线

1. 先补 parser 黄金集和外部评测适配，确保“字段可信”和“过程可观测”。
2. 再做异常 taxonomy、限流、配置 schema，这是从 demo 走向可试点的最低门槛。
3. 最后再拆 API 服务、数据库审计和租户隔离，这是从试点走向企业交付的门槛。

## 面试表达

FinTrace 当前不是我假装能替代金蝶/用友的完整费控产品，而是一个 AI PM/技术 PM 视角的可验证 MVP。它证明了我能把报销审核拆成阻断控制、确定性推理、LLM 增强、人机复核和红蓝评测闭环。

如果进入企业级团队，我最先补的不是“再加一个炫的 Agent”，而是 parser 黄金集、异常分类、外部评测适配、trace 可观察性和数据安全边界。因为企业客户真正买单的不是模型会说话，而是系统在真实数据、真实异常和真实审计压力下仍然可解释、可追溯、可回滚。
